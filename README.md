# Adrobot · Keitaro campaign tool

Небольшой веб-сервис поверх Admin API рекламного трекера **Keitaro** (10.3.x).

**Создаватор кампаний** (`/campaigns/new`). Пользователь вводит имя, выбирает страны и оффер
(автокомплит по имени или ID). Сервис создаёт в Keitaro кампанию с ротацией потоков по позиции,
моделью затрат CPC и стоимостью из параметра `cost`, а в ней два потока:
1. `regular` / `redirect`: фильтр `country accept [выбранные гео]`, редирект на `https://google.com`;
2. `default` / `landings`: выбранный оффер с долей 100 %.

Домен, группа и источник по умолчанию берутся из `.env` и меняются в форме (списки берутся из
`/domains`, `/groups`, `/traffic_sources`). Создание атомарно: если любой шаг упал, кампания
удаляется. После создания показываются ссылка на кампанию в админке Keitaro, URL кампании и
ссылка на редактор.

**Редактор** (`/campaigns`). Список кампаний с пагинацией и поиском, страница кампании с потоками.
Для оффер-потока показываются офферы (ID, название, доля, состояние); офферы можно добавлять
(тем же автокомплитом) и удалять. Доли после каждого изменения перераспределяются поровну и в сумме
всегда дают 100. На экране показывается то, что вернул Keitaro, а не локальные данные.

Все изменения пишутся в `audit_log` (кто, что, когда, payload до и после).

## Запуск

```bash
cp .env.example .env        # и вписать KEITARO_API_KEY
docker compose up --build
```

Открыть http://localhost:8000. Миграции применяются при старте контейнера (`alembic upgrade head`
в `CMD`). Вручную в docker:

```bash
docker compose exec app alembic upgrade head
```

### Локально без docker

Нужны Python 3.12 и PostgreSQL (`DATABASE_URL` в `.env`).

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
alembic upgrade head
uvicorn app.main:create_app --factory --reload
```

Postgres можно взять из compose: `docker compose up -d db` (порт наружу не проброшен; добавьте
`ports: ["5432:5432"]` к сервису `db`, если нужно).

### Тесты и линт

```bash
pytest
ruff check . && ruff format --check .
```

Тесты ходят в Keitaro только через моки `respx` (любой незамоканный запрос валит тест) и используют
SQLite во временной папке, Postgres для них не нужен.

### Probe API

`scripts/probe_keitaro.py` делает по одному GET на `/campaigns?limit=5`, `/offers`, `/domains`,
`/groups?type=campaigns`, `/traffic_sources` и сохраняет ответы в `scripts/samples/` (в `.gitignore`).
По ним построены схемы в `app/keitaro/schemas.py`. Повторно скрипт без `--force` не запускается,
чтобы не засорять журнал стенда.

```bash
python -m scripts.probe_keitaro
```

```
  services/

```

### JSON API

| Метод | Путь | |
|---|---|---|
| GET | `/api/offers?q=...` | до 20 офферов из кэша, поиск по имени и ID |
| POST | `/api/offers/refresh` | принудительно обновить кэш офферов |
| POST | `/api/campaigns` | `{"name", "geo": ["MX"], "offer_id", "domain_id"?, "group_id"?, "traffic_source_id"?}` |
| GET | `/api/campaigns/{id}` | кампания и потоки с названиями офферов |
| POST | `/api/campaigns/{id}/streams/{sid}/offers` | `{"offer_id"}` |
| DELETE | `/api/campaigns/{id}/streams/{sid}/offers/{offer_id}` | |

Ошибки отдаются как `{"detail": "..."}` с кодом 4xx/502. Swagger: http://localhost:8000/docs.

## Допущения и решения

**Доли.** `services/shares.py::distribute_shares(n)` делит 100 поровну, остаток от деления
раздаётся по 1 % первым офферам в порядке потока: 3 → 34/33/33, 7 → 15/15/14/14/14/14/14.
0 офферов дают `[]`, больше 100 офферов не разрешено (кому-то досталось бы 0 %). Удалить последний
оффер потока нельзя: `landings`-поток без офферов отправляет трафик в никуда, поэтому сначала нужно
добавить другой. Ручные (неравные) доли сбрасываются в равные при любом изменении; так задано в ТЗ.

**Запись в поток.** `PUT /streams/{id}` заменяет `offers` целиком, поэтому перед записью поток
перечитывается через `GET /streams/{id}`. Все поля офферов, кроме `share`, отправляются обратно как
есть (в том числе неизвестные нам), кроме служебных (`id`, `stream_id`, `created_at`, `updated_at`).
Повторное добавление оффера, который уже есть в потоке, даёт ошибку 409, дубля не будет. Поток
другой кампании или поток без офферов (`redirect`) редактировать нельзя. После PUT отрисовывается
ответ API.

**Откат.** Keitaro не умеет транзакций. Порядок: кампания → гео-поток → оффер-поток →
`GET /campaigns/{id}/streams` (проверка, что гео-поток первый) → запись в нашу БД. Если любой шаг
после создания кампании упал (ошибка API, таймаут, отмена запроса, сбой нашей БД), выполняется
`DELETE /campaigns/{id}` (удаляет и потоки). Если не удалось и удаление, кампания попадает в таблицу
`campaigns` со статусом `rollback_failed` и в лог с пометкой `ROLLBACK FAILED`, чтобы её можно было
найти и убрать. Все неудачи пишутся в `audit_log` (`campaign.create_failed`).

Позиции потоков передаются явно (`position: 1` и `2`), а порядок проверяется чтением потоков после
создания. Повторов запросов нет: POST не идемпотентен, а стенд журналирует каждый вызов.

**Валидация до записи.** Имя, коды стран (ISO 3166-1 alpha-2 по `pycountry`, приводятся к верхнему
регистру, дубли убираются), существование оффера, домена, группы и источника проверяются по кэшу
до первого запроса на запись: с неправильными данными в Keitaro не уходит ничего.

**Кэширование.**
- Офферы: таблица `offers_cache`, снимок целиком (`GET /offers` отдаёт весь список), обновляется
  лениво, если старше `OFFERS_CACHE_TTL` (по умолчанию час), или кнопкой «Refresh offers list» /
  `POST /api/offers/refresh`. Параллельные запросы обновляют кэш один раз (lock).
- Домены, группы, источники: в памяти процесса, TTL `REFERENCE_CACHE_TTL`. Они крошечные и меняются
  редко; при нескольких воркерах у каждого свой кэш, это допустимо.
- Кампании и потоки не кэшируются: редактор всегда работает с актуальным состоянием.

**Поиск кампаний.** У API нет серверного поиска. Числовой запрос ищет по ID
(`GET /campaigns/{id}`), текстовый фильтрует по имени последние `CAMPAIGN_SEARCH_LIMIT` (500)
кампаний одним запросом. Поиск запускается по кнопке, а не на каждое нажатие клавиши.

**Названия офферов.** Формат как в Keitaro: `[id] name`. На стенде имя оффера уже начинается с ID
(`18001 Detoxin ...`), дубль убирается: `[18001] Detoxin [HAIR-CL] ...`.

**Ошибки.** Ошибки API (4xx/5xx, таймауты, сеть) превращаются в `KeitaroError` с понятным
сообщением. Страницы показывают его в интерфейсе (htmx-фрагменты в блоке уведомлений), JSON API
отдаёт `{"detail"}` с 502/404, а не 500. Тело ошибки от Keitaro и наш запрос пишутся в лог
(`WARNING`). API-ключ не логируется.

**Кто изменил.** Авторизации в сервисе нет. `actor` в аудите берётся из заголовка `X-User` (его
может проставлять auth-прокси), иначе `anonymous@<ip>`.

**Статистика.** На стенде нет `/report/build`, поэтому колонок кликов, уников и ботов нет. В боевом
Keitaro их можно добавить одним запросом `POST /report/build` с группировкой по `offer_id` и фильтром
по `stream_id`.

## Расхождения с документацией / поведение стенда

Проверено одним чистым сценарием на стенде (создать кампанию → открыть в редакторе → добавить
оффер → удалить оффер), все запросы ответили 200:

- `POST /campaigns` принимает поля из документации: `type: "position"` (ротация по позиции),
  `cost_type: "CPC"`, `cost_auto: true` (стоимость из параметра `cost`), `domain_id`, `group_id`,
  `traffic_source_id`, и возвращает их сохранёнными, `alias` генерирует сам. Сервис всё равно
  сравнивает отправленное с сохранённым: если трекер молча проигнорирует поле, это попадёт в лог и
  в предупреждение на странице результата.
- `POST /streams` принимает явный `position`; `GET /campaigns/{id}/streams` возвращает гео-поток
  первым.
- Офферы потока приходят с полями `id`, `stream_id`, `created_at`, `updated_at`, `offer_id`,
  `share`, `state`; первые четыре служебные и при PUT не отправляются.
- `PUT /streams/{id}` с `offers` заменяет состав целиком и возвращает поток с новыми долями
  (50/50 после добавления второго оффера, 100 после удаления).
- Отличие от «боевых» данных: имена офферов на стенде начинаются с их ID (`18001 Detoxin ...`),
  см. «Названия офферов» выше.
- `GET /campaigns` на момент probe вернул пустой список: стенд показывает только свои кампании.

Расхождений с документацией Keitaro, требующих обходных решений, не найдено.

## Что сделал бы дальше

- Авторизация (SSO / basic за прокси) и роли; `actor` из реального пользователя.
- Статистика по офферам потока через `/report/build` с коротким кэшем.
- Ручное редактирование долей (с проверкой суммы 100) и пауза оффера в потоке без удаления.
- Optimistic locking: сравнивать `updated_at` потока между отрисовкой и записью и предупреждать,
  если поток успели поменять в админке.
- Фоновая задача, которая находит кампании `rollback_failed` и повторяет удаление.
- Кэш справочников в Redis при нескольких инстансах; метрики (Prometheus) по запросам к Keitaro.
- E2E-тест интерфейса (Playwright) и CI (ruff + pytest + сборка образа).
